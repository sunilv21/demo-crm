Implementation Status — Updated July 10, 2026

Since v1.0, a round of strengthening and feature work has shipped. This records what is now implemented, what was already present (or overstated in v1.0), what was intentionally skipped because it does not fit the Firestore + Next.js stack, and what remains. Section numbers reference the recommendations below.

✅ Implemented this cycle

  • Database indexing (§2.1) — composite indexes added to firestore.indexes.json and deployed to production: clients (assignedEmployees CONTAINS + createdAt DESC) and bookings (createdBy ASC + createdAt DESC). These differ from the v1.0 draft (see Corrections).
  • Query optimization / pagination (§2.2, partial) — Clients and Bookings lists no longer load the whole collection; they use server-side bounded loading (orderBy('createdAt','desc') + limit(100)) with a Load more button. Search/filters run over the loaded window.
  • Error boundary (§3.4) — added src/app/error.tsx, a route-level React error boundary with a friendly recovery UI; catches the FirestorePermissionError thrown by FirebaseErrorListener instead of white-screening.
  • User-friendly error surfacing (§3.3, partial) — the shared client form now toasts validation failures, so submissions no longer fail silently (fixed the public-intake "not submitting" issue; write/rules verified working).
  • Dark mode (§5.3) — next-themes wired into the root layout; Light / Dark / System switcher in the sidebar. The dark palette already existed under .dark in globals.css.
  • Accessibility (§5.4, partial) — "Skip to main content" link added (targeting #main-content); aria-labels added to the icon-only ⋯ action menus on the primary list pages. Radix already provides modal focus-trap, ARIA, and keyboard navigation.
  • Offline support (§5.2) — Firestore IndexedDB persistence enabled via persistentLocalCache + persistentMultipleTabManager in getSdks() (multi-tab safe), plus a NetworkStatusListener that toasts on offline/online.
  • Code splitting (§2.5, partial) — the ~400KB xlsx library is now lazy-loaded (await import('xlsx')) only when a file is imported.

🟡 Already present / overstated in v1.0

  • Loading states (§5.1) — already implemented; ~28 files use skeleton loaders.
  • Centralized error handling (§3.1) — app already has errorEmitter, typed FirestorePermissionError, and FirebaseErrorListener. The HTTP 400/401/403 error classes in the draft are for REST backends and do not fit a client-side Firestore app.
  • Query projection (§2.2) — the select() field-projection example is not supported by the Firestore Web SDK.
  • Client-side TTL cache (§2.3) — redundant with Firestore realtime listeners (which cache locally). Intentionally not implemented.

⬜ Not yet done (still recommended)

  • Security §1.1, §1.3, §1.5 — password policy, audit logging, idle session timeout: pending. §1.2 (account lockout) and §1.4 (field encryption) are intentionally NOT recommended as drafted — see note.
  • Backups §4 — none yet. Recommendation: use Firebase managed Point-in-Time Recovery + scheduled exports rather than custom Cloud-Functions backup.
  • Testing §6 — no unit / component / E2E tests yet (dedicated setup effort).
  • Image optimization §2.4 — not done. Code splitting §2.5 — partial (xlsx lazy-loaded; dialogs could still be split).

Why §1.2 and §1.4 are not recommended as written: the §1.4 encryption sample uses NEXT_PUBLIC_ENCRYPTION_KEY — a key shipped to the browser gives no real protection (security theater); genuine field encryption needs server-side keys (Cloud Functions / KMS). And §1.2's Firestore-based lockout is client-bypassable and weaker than the brute-force throttling Firebase Auth already enforces server-side.

Corrections to v1.0

  • The §2.1 index draft proposed 3-field indexes plus bookings(clientId+status+startDate) and invoices(clientId+status+dueDate). Those were not used — the app filters status/type/visa/org/date client-side, so only 2-field ordering indexes are required, and those shipped. The invoices and clientId+status+startDate indexes back queries that do not exist in the code and were omitted.
  • The ordered list queries only return documents that have a createdAt field — legacy records missing it will not appear in the paginated lists (all app-created records have it).

New features delivered this cycle (beyond the strengthening scope)

  • Corporate Organizations — organizations collection; clients link via Client.organizationId; org roll-up page with per-client booking totals; org rules deployed.
  • Client bulk import — CSV / Excel importer (xlsx) on the Clients page and per-organization, with template + preview.
  • Organization-scoped intake link — "Share Intake Form" produces /intake?org=<id>; public submissions auto-link to that org.
  • Booking archival — manual archive of paid bookings + auto-archive 15 days after payment; Travel History view; multi-select ("print 3 of 5") printing.
  • Booking date fix — one-way flights no longer render a phantom "1 Jan 1970" return date; missing return date auto-flags one-way.
  • Attendance — admins can Mark Present for any employee (rule fixed & deployed) and manage per-day break minutes.
  • Clients date-range filter — filter by Date Created.

1. Security Strengthening

Current Security State

Strengths:

  • Firebase Authentication with email/password
  • Firestore security rules for data access
  • Role-based access control (admin/manager/employee/agent)
  • Input validation with Zod

Gaps:

  • No password complexity requirements
  • No account lockout mechanism
  • No security audit logging
  • Limited session management
  • No data encryption for sensitive fields

Recommended Security Improvements

1.1 Password Policy Enhancement

Severity: HIGH | Effort: 1 week | Impact: Account security

Implement strong password requirements with validation:

  • Minimum 12 characters
  • At least one uppercase letter
  • At least one lowercase letter
  • At least one number
  • At least one special character

1.2 Account Lockout Mechanism

Severity: HIGH | Effort: 1 week | Impact: Prevent brute force attacks

Implement account lockout after failed login attempts:

  • 5 failed attempts trigger 15-minute lockout
  • Automatic lockout expiration
  • Reset on successful login
  • User-friendly lockout messages

1.3 Security Audit Logging

Severity: HIGH | Effort: 2 weeks | Impact: Compliance and security monitoring

Log all security-relevant events:

  • User login/logout events
  • User creation, updates, deletions
  • Client and booking modifications
  • Permission changes
  • Data exports
  • Include IP address and user agent

1.4 Sensitive Data Encryption

Severity: MEDIUM | Effort: 2 weeks | Impact: Data protection compliance

Encrypt sensitive fields like passport numbers:

  • AES-256-GCM encryption
  • Secure key management
  • Transparent encryption/decryption
  • Environment-based key configuration

1.5 Session Management

Severity: MEDIUM | Effort: 1 week | Impact: User session security

Implement session timeout and management:

  • 30-minute session timeout
  • 5-minute warning before timeout
  • Activity-based timer reset
  • Automatic logout on timeout
