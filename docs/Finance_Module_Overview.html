1. TL;DR

The Finance module is a cash-flow ledger layered on top of the CRM: every rupee lives in an account, every movement is one transaction (income / expense / transfer), and account balances derive from those transactions. It answers: how much do we have, where is it, where did it come from, where did it go, and who got paid.

The good news: your app already has the raw materials — a per-booking payment ledger, a PaymentMode enum, supplier fields on bookings, a just-built refund workflow, and a role system. The Finance module mostly consolidates these into a single transaction engine plus new master data (accounts, suppliers, categories). Two things need a real decision before building: who is allowed to see company money (your revenue data is currently agent-only) and how balances stay correct (your current writes are fire-and-forget). Both are covered in §6.

Navigation

Add a collapsible Finance group to the sidebar (app-sidebar-nav.tsx) — exactly like the existing Employee Management group — visible to Admin/Manager (and Employee for "create" screens). Items: Dashboard · Money In · Money Out · Transfers · Accounts · Transactions · Suppliers · Reports · Settings.

Routes follow the existing src/app/(app)/… convention; each page uses the same useCollection/useDoc + non-blocking-write pattern as Clients/Bookings.

4. Data model & how balances work

Five new collections, all following the app's existing doc conventions (createdAt/createdBy/updatedBy, string ids):

CollectionPurposeLinks to existing
accountsCash / bank / wallet buckets that hold money—
payment_methodsConfigurable in/out methods (supersedes the hard-coded PaymentMode)generalises PaymentMode
suppliersPayee directory (VFS, airlines, rent, salary…)replaces free-text booking.supplierName
expense_categoriesVisa fees, air ticket, rent, salary…—
transactionsThe engine. One doc per income/expense/transferclientId, bookingId, invoiceId, supplierId, accountId

Recommended balance strategy: compute on read, don't mutate

The spec keeps a stored currentBalance and mutates it on every transaction. In this app's fire-and-forget write model that is a race-condition risk (two writes clobber the balance). Your app already computes money on read elsewhere (organization roll-ups sum booking totals live). Do the same here:

Account balance = openingBalance + Σ(income to this account) − Σ(expense from this account) + Σ(transfers in) − Σ(transfers out)

Compute per-account balances by reading that account's completed transactions. It's always correct, needs no atomic increments, and matches the existing pattern. If real-time performance later demands a cached currentBalance, update it inside a Firestore runTransaction (a deliberate departure from the current non-blocking writes) or a Cloud Function trigger — not a plain setDoc.

5. Integration flows

Money In — reuse the booking payment ledger

Client → Booking → Payments dialog (existing) → records payment[] │ ▼ (also emit) transaction { type:'income', clientId, bookingId, accountId, paymentMethodId, amount, reference, receivedBy }

The booking Payments dialog already captures amount/date/mode/reference. Extend it (or the Money-In screen) to also pick an account and write a linked income transaction. That keeps the booking's own balance accurate and feeds company cash flow from one action — no double entry by staff.

Money Out — expenses, supplier payments & refunds

  • Supplier / expense payment: new screen → expense transaction from an account, tagged with supplierId + categoryId.
  • Refund payout: when the booking refund (already built) is marked processed, emit an expense transaction (money leaving an account back to the customer) so cash flow reflects it.
  • Salary: payroll (existing HR module) can post expense transactions per pay run — a natural later tie-in.

Transfers

A transfer writes one transaction that debits one account and credits another; it never appears as income or expense in reports.

6. Decisions to make before building

6.1 — Who can see company money? (the big one)

Today, revenue/profit is agent-only in this app: canViewRevenue = isAgent, and even admins cannot see booking revenue/profit — this is intentional and enforced across Bookings, the Organizations roll-up, etc. The Finance module, however, is fundamentally about company cash flow, and the spec grants Admin full access. These directly conflict.

Options:

  • (a) Make Finance a deliberate exception — Admin/Manager see all accounts & balances.
  • (b) Scope Finance to the same agent-only visibility (limiting — agents aren't bookkeepers).
  • (c) ✅ Recommended — add a dedicated finance role. Introduce a new role (Finance / Accountant) alongside admin·manager·employee·agent. Company cash flow becomes finance-role-only (plus admin); per-booking profit margin stays agent-only, completely unchanged. The two money views never collide because they belong to different roles.

What option (c) touches

  • Add 'finance' to the Role type (types.ts, use-app-user.tsx) + a new canViewFinance gate (parallel to canViewRevenue).
  • Firestore rules helper isFinance() for the finance collections; add finance to the /users/new role dropdown; show the Finance nav group to the role.

Sub-decisions: finance also gets read access to clients/bookings/invoices (to link payments) but not HR/users; admin keeps full finance access (superuser); finance does not see per-booking profit margin (that stays agent-only — cash movements ≠ sales margin).

6.2 — Balance integrity vs. the current write model

The app uses non-blocking (fire-and-forget) writes with no transactions. The Finance spec demands atomic balance updates and immutable completed records. Adopt compute-on-read balances (§4) and treat completed transactions as append-only — corrections happen via reversal/adjustment transactions, never edits. This is a new discipline; the rest of the app edits freely.

6.3 — One ledger or two? (booking payments vs finance transactions)

Bookings already store payments[]. If Money In also writes a transaction, the same receipt exists in two places. Resolve up front: the booking ledger stays the operational record (what the customer owes on this booking); the finance transaction is the cash-flow record (what hit which account). Recording a booking payment should auto-create the linked transaction so staff never enter it twice, and the two are reconciled by bookingId.

6.4 — Security rules & approvals

New collections need Firestore rules mirroring the app's pattern: signed-in reads scoped by role; employees create but cannot delete/approve; admin/manager approve. The Draft→Pending→Completed→Cancelled status machine and the "approvedBy" step are new — the app has no approval workflow today, so this is genuinely new UI + rules.

Two orthogonal money gates: canViewRevenue (agent → per-booking margin) and the new canViewFinance (admin + finance → company cash flow). They never overlap.

8. Suggested phased rollout

  1. Foundation: accounts + transactions collections, rules, and the Transactions ledger page with compute-on-read balances. Nothing else works without these.
  2. Master data: suppliers, expense_categories, payment_methods + a Settings page.
  3. Money In: wire the existing booking Payments flow to also emit income transactions (§6.3).
  4. Money Out: expenses/supplier payments, and tie in the existing refund payout.
  5. Transfers + Dashboard/Reports (KPIs, cash-flow charts) on top of the transaction data.
  6. Later: approval workflow polish, payroll→expense tie-in, GST/P&L (the spec's "future" list).
