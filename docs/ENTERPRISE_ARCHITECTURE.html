Executive Summary

Document Purpose

This Enterprise Architecture Document provides a comprehensive technical blueprint for the Sky Visa CRM system, a complex multi-domain application integrating Travel Management, Visa Processing, Customer Relationship Management (CRM), Human Resources (HR), Finance, and Collections functionality.

System Scope

The Sky Visa CRM is a single-tenant (with multi-tenant migration path) travel agency management system that handles:

  • Travel Management: Flight bookings, hotel reservations, car rentals, activities
  • Visa Processing: Visa applications, document tracking, embassy coordination
  • CRM: Lead management, customer tracking, follow-ups, communication
  • HR: Employee management, attendance tracking, leave management
  • Finance: Invoicing, payments, profit tracking, accounting
  • Collections: Payment collection, debt management, reconciliation

Architecture Highlights

  • Database: Firebase Firestore (NoSQL) with 17+ collections
  • Frontend: Next.js 16 with React 19, TypeScript 5
  • Backend: Firebase Functions with serverless architecture
  • Real-time: Firestore real-time listeners for live updates
  • Offline: IndexedDB persistence for offline functionality
  • Security: Firebase Authentication + Firestore Security Rules
  • Scalability: Serverless architecture with auto-scaling capabilities

Key Architectural Decisions

  1. NoSQL Database: Chosen for flexibility in evolving travel industry requirements
  2. Serverless Backend: Reduces operational overhead and provides auto-scaling
  3. Real-time First: Enables collaborative features and live updates
  4. Offline-First: Critical for travel agents working in connectivity-challenged environments
  5. Modular Design: Domain-driven design approach for maintainability

Migration Readiness

The architecture is designed with multi-tenant migration in mind, including:

  • Tenant-aware data modeling patterns
  • Isolation strategies (database vs. schema-based)
  • Migration pathways with zero-downtime considerations
  • Cost optimization for multi-tenant scenarios

Architecture Principles

1. Modularity

Principle: The system is organized into cohesive, loosely coupled modules based on business domains.

Implementation:

  • Domain-driven design (DDD) boundaries
  • Clear separation of concerns
  • Independent module deployment capability
  • Minimal inter-module dependencies

Benefits: Easier maintenance, parallel development, independent scaling, clear ownership

2. Scalability

Principle: The architecture supports horizontal scaling and can handle growth in users, data, and traffic.

Implementation:

  • Serverless backend (Firebase Functions)
  • Auto-scaling database (Firestore)
  • Stateless application design
  • Efficient query patterns with indexes

Benefits: Automatic scaling, cost efficiency, no capacity planning required, handles traffic spikes

3. Reliability

Principle: The system maintains availability and data integrity even in the face of failures.

Implementation:

  • Automated backup systems
  • Error handling and retry logic
  • Offline persistence
  • Data validation at multiple layers

Benefits: High availability, data protection, graceful degradation, quick recovery

4. Security

Principle: Security is built into every layer of the architecture.

Implementation:

  • Defense in depth approach
  • Least privilege access
  • Comprehensive audit logging
  • Regular security reviews

Benefits: Data protection, regulatory compliance, risk mitigation, trust assurance

5. Maintainability

Principle: The codebase and architecture are designed for long-term maintainability.

Implementation:

  • Clean code practices
  • Comprehensive documentation
  • Automated testing
  • Code review processes

Benefits: Reduced technical debt, faster onboarding, easier debugging, sustainable development

6. Performance

Principle: The system is optimized for performance at every layer.

Implementation:

  • Efficient database queries
  • Caching strategies
  • Code splitting and lazy loading
  • Image optimization

Benefits: Better user experience, lower infrastructure costs, higher throughput, competitive advantage

7. Flexibility

Principle: The architecture can adapt to changing business requirements.

Implementation:

  • Schemaless database design
  • Plugin architecture
  • Configuration-driven features
  • Extensible security model

Benefits: Faster feature delivery, business agility, future-proofing, competitive responsiveness

Collection Relationships Summary

Primary Relationships:

  1. Users → Attendance (One-to-Many) - User can have multiple attendance records
  2. Users → Leaves (One-to-Many) - User can have multiple leave requests
  3. Users → Bookings (One-to-Many) - User creates multiple bookings
  4. Clients → Bookings (One-to-Many) - Client can have multiple bookings
  5. Clients → Customer Logs (One-to-Many) - Client can have multiple activity logs
  6. Clients → Follow Ups (One-to-Many) - Client can have multiple follow-ups
  7. Organizations → Clients (One-to-Many) - Organization can have multiple clients
  8. Bookings → Invoices (One-to-Many) - Booking can have multiple invoices
  9. Leads → Clients (One-to-One, Optional) - Lead can be converted to a client

Many-to-Many Relationships:

  1. Clients ↔ Users (Many-to-Many) - Client can be assigned to multiple employees
  2. Bookings ↔ Payments (Many-to-Many) - Booking can have multiple payments

Data Consistency Rules

Referential Integrity:

  1. When a user is deleted, their attendance and leave records should be archived
  2. When a client is deleted, related bookings should be archived
  3. When a booking is deleted, related invoices should be archived
  4. Lead conversion should create a client and update lead status

Cascade Operations:

  1. Soft Delete: Mark documents as archived instead of hard delete
  2. Archive Exemption: Certain documents can be marked as exempt from archival
  3. Timestamp Tracking: All operations should track who made changes and when

Denormalization Strategy:

  1. Client Name: Denormalized in bookings, invoices, customer_logs, follow_ups
  2. User Name: Denormalized in attendance, leaves, customer_logs
  3. Booking ID: Referenced in invoices
  4. Rationale: Reduce read operations and improve query performance

Domain-Driven Design (DDD)

Bounded Contexts

The Sky Visa CRM is organized into the following bounded contexts:

1. User Management Context

Purpose: Manage user accounts, authentication, and authorization

Core Entities: User, Role, Permission

Key Operations: User registration, Authentication, Role assignment, Permission management

Ubiquitous Language:

  • User: Person with system access
  • Role: Set of permissions (employee, manager, admin, agent)
  • Authentication: Process of verifying identity
  • Authorization: Process of granting access

Domain Events: UserCreated, UserUpdated, UserDeleted, RoleChanged, PermissionGranted, PermissionRevoked

2. Customer Management Context

Purpose: Manage customer lifecycle from lead to loyal customer

Core Entities: Lead, Customer (Client), Organization, CustomerLog, FollowUp

Key Operations: Lead creation, Lead conversion, Customer profile management, Activity logging, Follow-up scheduling

Ubiquitous Language:

  • Lead: Potential customer
  • Customer: Active client
  • Conversion: Process of turning lead into customer
  • Activity: Interaction with customer
  • Follow-up: Scheduled contact with customer

Domain Events: LeadCreated, LeadConverted, CustomerCreated, CustomerUpdated, ActivityLogged, FollowUpScheduled, FollowUpCompleted

3. Booking Management Context

Purpose: Manage travel bookings across all service types

Core Entities: Booking, FlightBooking, HotelBooking, VisaBooking, Payment, Document

Key Operations: Booking creation, Booking modification, Payment processing, Document upload, Status updates

Ubiquitous Language:

  • Booking: Reservation for travel service
  • Sector: Flight segment (for multi-city flights)
  • Payment: Financial transaction for booking
  • Document: Supporting document for booking
  • Status: Current state of booking

Domain Events: BookingCreated, BookingUpdated, BookingConfirmed, BookingCancelled, PaymentReceived, PaymentRefunded, DocumentUploaded, StatusChanged

4. Invoice Management Context

Purpose: Manage invoicing and billing

Core Entities: Invoice, InvoiceItem, Payment

Key Operations: Invoice generation, Invoice delivery, Payment tracking, Overdue management

Ubiquitous Language:

  • Invoice: Bill for services
  • Due Date: Payment deadline
  • Overdue: Past due date
  • Paid: Fully settled
  • Partial: Partially paid

Domain Events: InvoiceGenerated, InvoiceSent, PaymentReceived, InvoiceOverdue, InvoicePaid

5. HR Management Context

Purpose: Manage employee operations and HR processes

Core Entities: Employee (User), Attendance, Leave, Holiday, Break

Key Operations: Attendance tracking, Leave request management, Holiday management, Work time calculation

Ubiquitous Language:

  • Attendance: Record of employee presence
  • Punch In: Start of work day
  • Punch Out: End of work day
  • Leave: Requested time off
  • Holiday: Company-observed holiday
  • Break: Temporary pause in work

Domain Events: AttendanceRecorded, LeaveRequested, LeaveApproved, LeaveRejected, PunchIn, PunchOut, BreakStarted, BreakEnded

6. Process Tracking Context

Purpose: Track business processes and workflows

Core Entities: Process, ProcessStep, ProcessInstance

Key Operations: Process definition, Process execution, Step completion, Process monitoring

Ubiquitous Language:

  • Process: Business workflow
  • Step: Individual task in process
  • Instance: Execution of a process
  • Status: Current state of process

Domain Events: ProcessStarted, ProcessCompleted, StepStarted, StepCompleted, ProcessFailed

users Collection Schema

{

  createdAt: Timestamp
  updatedAt: Timestamp
  createdBy: string
  updatedBy: string

Security Rules: Read: All signed-in users, Create: Self-create only, Update: Self-update (except role, salary, work times - admin only), Delete: Admin only

Module 6: Document Generation & AI Extraction

Collections: none. Unlike Modules 1–5, this module owns no Firestore collections — it is a stateless generation layer that reads existing Booking/Client documents (or, for the Other Format itinerary, purely client-local draft state) and returns a file at request time. Nothing it produces is persisted server-side.

Shared rendering primitives — src/app/actions/docx-helpers.ts: the navy/gold visual system, a fixedTable() wrapper (Word's default "autofit" table layout otherwise shrinks single-cell banner tables to their text width), and a PAGE_WIDTH = 11000 DXA constant — the true printable width for both documents' US Letter / 620-twip-margin page setup, so every table aligns with the letterhead's gold rule.

Hotel Voucher Generator — src/app/actions/voucher-docx.ts (Server Action generateBookingVoucherDocx): produces a real Word (.docx) hotel booking voucher matching the agency's reference layout. Hotel bookings only — rejects any other bookingType. Uses the COMPANY identity (same as existing receipts/printables). Reads bookingDetails.hotelAddress / bookingDetails.hotelTel from the booking form, rendering "—" when blank rather than omitting the line.

Itinerary "Other Format" Generator — src/app/actions/itinerary-docx.ts (Server Action generateOtherFormatDocx): a second, freeform itinerary layout — distinct from the structured Itinerary Builder that persists to clients/{clientId}/itineraries/{itineraryId} — for hotel/tour package quotes. Uses a separate AGENCY identity by design.

AI Paste-and-Extract — src/app/actions/itinerary-format.ts (Server Action extractOtherFormatItinerary): takes raw pasted itinerary text and an ExtractionProvider ('gemini' | 'nvidia', defaults to 'nvidia'), returning the same shape regardless of provider. Both providers are extractive (not generative) and share one Zod output schema, so unmentioned fields come back blank rather than fabricated. Transient provider errors (429/503/504) surface as a retry-friendly message.

Client-local persistence — src/hooks/use-persisted-state.ts: a localStorage-backed hook keeps the Other Format editor's draft state alive across navigation, so an in-progress or AI-extracted draft isn't lost and reopening the tab doesn't force a second (paid) AI extraction call.

Security Rules Architecture

Security Principles

  1. Least Privilege: Users only have access to data they need
  2. Defense in Depth: Multiple layers of security
  3. Audit Trail: All access is logged
  4. Data Isolation: Tenant data is isolated (future multi-tenant)
  5. Role-Based: Access based on user roles

Collection-Specific Security Rules

Users Collection

match /users/{userId} {
  // Read: All signed-in users can read user profiles
  allow read: if request.auth != null;
  
  // Create: Users can create their own account
  allow create: if request.auth.uid == userId;
  
  // Update: Users can update their own profile
  // Admins can update any user
  allow update: if request.auth.uid == userId || 
                   request.auth.token.role == 'admin';
  
  // Delete: Only admins can delete users
  allow delete: if request.auth.token.role == 'admin';
}

Clients Collection

match /clients/{clientId} {
  // Helper function to check if user is assigned to client
  function isAssignedUser() {
    return request.auth.uid in resource.data.assignedEmployees;
  }
  
  // Helper function to check if user created the client
  function isCreator() {
    return request.auth.uid == resource.data.createdBy;
  }
  
  // Helper function to check if user is admin or manager
  function isAdminOrManager() {
    return request.auth.token.role in ['admin', 'manager'];
  }
  
  // Read: Assigned users, creator, or admin/manager
  allow read: if isAssignedUser() || 
               isCreator() || 
               isAdminOrManager();
  
  // Create: Any signed-in user or public form (with validation)
  allow create: if request.auth != null || 
                  request.resource.data.source == 'public';
  
  // Update: Assigned users, creator, or admin/manager
  allow update: if isAssignedUser() || 
                isCreator() || 
                isAdminOrManager();
  
  // Delete: Only admin or manager
  allow delete: if isAdminOrManager();
}

Attendance Collection

match /attendance/{attendanceId} {
  // Extract userId from attendanceId format: {userId}_{YYYY-MM-DD}
  function getUserIdFromId() {
    return attendanceId.split('_')[0];
  }
  
  // Helper function to check if user owns the attendance record
  function isOwner() {
    return request.auth.uid == getUserIdFromId();
  }
  
  // Get: Admin or owner
  allow get: if request.auth.token.role == 'admin' || 
              isOwner();
  
  // List: Admin or owner (filtered by userId)
  allow list: if request.auth.token.role == 'admin' ||
                request.query.limit <= 50;
  
  // Create: Admin or owner (deterministic ID)
  allow create: if request.auth.token.role == 'admin' ||
                   request.auth.uid == getUserIdFromId();
  
  // Update: Admin or owner (punchIn and date are locked)
  allow update: if request.auth.token.role == 'admin' ||
                (isOwner() && 
                 request.resource.data.punchIn == resource.data.punchIn &&
                 request.resource.data.date == resource.data.date);
  
  // Delete: Only admin
  allow delete: if request.auth.token.role == 'admin';
}

Audit Logs Collection

match /audit_logs/{auditLogId} {
  // Read: Only admins
  allow read: if request.auth.token.role == 'admin';
  
  // Write: Only system (via backend functions)
  // No client-side writes allowed

}

Cost Optimization Strategies

Firestore Cost Structure

Read Operations: Charged per document read, Real-time listeners charged per read

Write Operations: Charged per document write, Array operations count as 1 write

Delete Operations: Charged per document delete, Bulk delete counts as multiple deletes

Storage: Charged per GB stored, Includes document data and indexes

Optimization Strategies

1. Read Optimization

  • Selective Field Retrieval: Retrieve only needed fields
  • Pagination: Limit results and implement pagination
  • Caching: Implement client-side caching
  • Real-time Listener Optimization: Don't include metadata changes

2. Write Optimization

  • Batch Writes: Use batch writes for multiple operations
  • Conditional Updates: Use update with field masks
  • Array Operations: Use arrayUnion/arrayRemove for single write

3. Storage Optimization

  • Document Size Reduction: Remove unnecessary fields, use short field names
  • Index Optimization: Remove unused indexes, limit composite index fields
  • Data Archival: Archive old data to reduce active storage

4. Query Optimization

  • Efficient Queries: Use indexes for queries, limit query results
  • Query Batching: Batch multiple queries

Multi-Tenant Migration Path

Migration Strategy Overview

Current State: Single-tenant architecture

Target State: Multi-tenant SaaS platform

Migration Approach: Phased migration with zero downtime

Tenant Isolation Models

Option 1: Database-Per-Tenant (Recommended for Enterprise)

Architecture: Separate Firestore databases per tenant

Pros: Complete data isolation, Independent scaling, Separate backups, Easier compliance

Cons: Higher infrastructure cost, Complex management, Cross-tenant queries difficult

Option 2: Schema-Based Isolation (Recommended for MVP)

Architecture: Single database with tenant ID in all documents

Pros: Lower infrastructure cost, Easier management, Simpler implementation, Faster migration

Cons: Shared resources, Potential for data leakage, Complex security rules, Limited isolation

  • Create default tenant for existing data

  • Add tenant-specific branding

Phase 3: Feature Rollout (1-2 months)

  • Add tenant-specific features
  • Test multi-tenant functionality

Phase 4: Optimization (1 month)

  • Optimize multi-tenant performance

  • Optimize costs

Recovery Procedures: Identify failure scope, Select appropriate backup, Restore data, Verify integrity, Update applications

Testing

Regular Testing: Monthly backup restoration tests, Quarterly failover drills, Annual disaster recovery simulation

Documentation: Recovery procedures, Contact information, Escalation procedures, Communication plan
